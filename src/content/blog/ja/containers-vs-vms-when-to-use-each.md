## はじめに

セキュリティ分離レベル、リソースオーバーヘッド、そして日々の運用管理：コンテナと仮想マシン（VM）の技術的トレードオフを客観的に比較し、どちらか一方、あるいは両方の併用を確信を持って選択するための実戦ガイドです。本ガイドでは、基本概念からトレードオフ、今週から現場へ導入できる本番仕様のワークフローまでを詳しく解説します。

## なぜ重要なのか

- **開発者ベロシティの向上**: 開発機、CI パイプライン、本番環境の完全な環境一致性を担保し、「自分のマシンでは動いた」を撲滅します。
- **システムの信頼性向上**: 厳格なマルチテナント分離や非信頼コードの実行時、ハイパーバイザーレベルの強固なハードウェア境界で安全を確保します。
- **コストコントロール**: コンテナの高密度集約によりサーバー台数を圧縮し、インフラコストを最適化します。

## コアコンセプト

### 1. 最小の実装スライスから着手する

全システムを一気にコンテナ化または VM 移行する前に、まずはエンドツーエンドで動作する単一のバーティカルスライスを完成させます。**コンテナ vs VM:使い分け**においては、単一のステートレスサービスを対象に検証を行い、初日から可観測性を確立することを意味します。

### 2. 「成功の落とし穴」を広く設ける

開発者が個別に Dockerfile を乱立させるのではなく、軽量で安全なベースイメージ（Distroless 等）と統一された CI ビルドを整備します。本番対応の最小スターター構成例：

```typescript
// Minimal production-ready starter
export const config = {
  retries: 3,
  timeoutMs: 5_000,
  circuitBreaker: { failures: 5, cooldownMs: 30_000 },
};

export async function runWithResilience<T>(fn: () => Promise<T>): Promise<T> {
  let lastError: unknown;
  for (let attempt = 1; attempt <= config.retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      await new Promise((r) => setTimeout(r, attempt * 250));
    }
  }
  throw lastError;
}
```

### 3. 真に重要な指標を計測する

| 指標 | 推奨される初期ターゲット |
| --- | --- |
| p95 レイテンシ | < 300 ms |
| エラーバジェット消費率 | < 2% / 30 日 |
| デプロイ頻度 | 毎日 (Daily) |
| ロールバック所要時間 | < 10 分 |

## 本番チェックリスト

1. ホストノード名とコンテナ ID を付与した構造化ログを導入する。
2. 障害発生時に安全にコンテナを再起動・退避できるオーケストレーター機能フラグを設定する。
3. リリース前にメモリ制限（OOM）到達時のコンテナの挙動とグレースフルシャットダウンを検証する。
4. 発生頻度の高い上位 3 つの障害シナリオ（イメージプル失敗、ノードリソース枯渇、PID 枯渇）に対する運用手順書（Runbook）を整備する。

## よくある落とし穴

> 実際のユーザーが付く前にプラットフォームを過剰に作り込まないこと。早期に選んだ技巧的な技術よりも、適切に選ばれた堅実な技術のほうが遥かに成果を生みます。

- 肥大化したレガシーモノリスをそのまま単一コンテナに押し込み、VM のような運用を続けること。
- 非信頼のサードパーティコードを通常のコンテナ名前空間だけで実行し、カーネル脱獄リスクを放置すること。
- 深夜の緊急呼び出しにつながる cgroup メモリ枯渇アラートの未設定。
