## はじめに

無料トライアル、日割り計算（Proration）、決済失敗時の督促フロー（Dunning）、そして Webhook の冪等処理：財務チームや監査法人が完全に信頼できるサブスクリプション課金システムを構築します。本ガイドでは、基本概念からトレードオフ、今週から現場へ導入できる本番仕様のワークフローまでを詳しく解説します。

## なぜ重要なのか

- **開発者ベロシティの向上**: 厳密な状態遷移モデルを敷くことで、手動での決済ログ照合作業や二重課金のトラブルシューティングをなくします。
- **システムの信頼性向上**: 外部決済プロバイダー（Stripe 等）の瞬断や Webhook の遅延・再送にも耐えうる冪等性を担保します。
- **コストコントロール**: 回収不能な未払いを自動督促で最小化し、不要な返金手数料やチャージバック損失を抑制します。

## コアコンセプト

### 1. 最小の実装スライスから着手する

複雑な複数通貨プランやカスタム請求書発行を作る前に、まずはエンドツーエンドで動作する単一のバーティカルスライスを完成させます。**サブスク課金システムの作り方**においては、単一通貨の定期決済と Webhook によるアカウント権限の更新フローを可観測性付きで確立することを意味します。

### 2. 「成功の落とし穴」を広く設ける

個々のエンドポイントで個別に決済イベントをパースするのではなく、イベント ID に基づく重複排除とトランザクション処理を共通化します。本番対応の最小スターター構成例：

```typescript
// Minimal production-ready starter
export const config = {
  retries: 3,
  timeoutMs: 5_000,
  circuitBreaker: { failures: 5, cooldownMs: 30_000 },
};

export async function runWithResilience<T>(fn: () => Promise<T>): Promise<T> {
  let lastError: unknown;
  for (let attempt = 1; attempt <= config.retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      await new Promise((r) => setTimeout(r, attempt * 250));
    }
  }
  throw lastError;
}
```

### 3. 真に重要な指標を計測する

| 指標 | 推奨される初期ターゲット |
| --- | --- |
| p95 レイテンシ | < 300 ms |
| エラーバジェット消費率 | < 2% / 30 日 |
| デプロイ頻度 | 毎日 (Daily) |
| ロールバック所要時間 | < 10 分 |

## 本番チェックリスト

1. 顧客 ID、サブスクリプション ID、Webhook イベント ID を付与した構造化ログを導入する。
2. 価格プラン変更時に即座に旧プランへ戻せるキルスイッチ付きの機能フラグ（Feature Flag）を設定する。
3. リリース前に決済失敗、カード有効期限切れ、日割りアップグレードのシミュレーションを実施する。
4. 発生頻度の高い上位 3 つの障害シナリオ（Webhook 署名不一致、未処理イベントの滞留、二重決済）に対する運用手順書（Runbook）を整備する。

## よくある落とし穴

> 実際のユーザーが付く前にプラットフォームを過剰に作り込まないこと。早期に選んだ技巧的な技術よりも、適切に選ばれた堅実な技術のほうが遥かに成果を生みます。

- Webhook イベントが常に順番通りに届くと仮定し、順不同の到着でステータスを壊すこと。
- クライアント側から送信された決済完了通知をそのまま信用し、サーバー側での検証を怠ること。
- 深夜の緊急呼び出しにつながる決済失敗率急増アラートの未設定。

## まとめ

**サブスク課金システムの作り方**は、小さく観測可能なステップで反復を重ねるチームに大きな成果をもたらします。上記のチェックリストを起点に、週に 1 つの課題を自動化し、エンジニアリングの成功を積み重ねていきましょう。
