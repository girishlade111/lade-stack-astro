## はじめに

プロンプトエンジニアリングとファインチューニングの使い分け、高品質なドメイン特化データセットの構築手法、そして低予算の GPU リソースで実現する LoRA（Low-Rank Adaptation）ワークフローまで：実務で成果を出すための LLM 最適化ガイドです。本ガイドでは、基本概念からトレードオフ、今週から現場へ導入できる本番仕様のワークフローまでを詳しく解説します。

## なぜ重要なのか

- **開発者ベロシティの向上**: 専門用語や独自の出力フォーマットをモデルに事前学習させることで、毎回長大なプロンプトを組み立てる手間を解消します。
- **システムの信頼性向上**: JSON や SQL などの厳格な構文制約への準拠率を高め、後続処理でのパースエラーを低減します。
- **コストコントロール**: 小型モデル（7B / 14B 等）を特化調整することで、高価な大型商用 API の利用料を大幅に削減します。

## コアコンセプト

### 1. 最小の実装スライスから着手する

数十万件のデータセットを用意する前に、まずはエンドツーエンドで動作する単一のバーティカルスライスを完成させます。**ドメイン特化LLMのファインチューン**においては、人手で厳選した 100〜200 件の高品質サンプルで LoRA 学習を回し、初日から評価指標（Evals）の可観測性を確立することを意味します。

### 2. 「成功の落とし穴」を広く設ける

場当たり的なトレーニングスクリプトに頼るのではなく、データ検証パイプラインと自動ベンチマークを CI に組み込みます。本番対応の最小スターター構成例：

```typescript
// Minimal production-ready starter
export const config = {
  retries: 3,
  timeoutMs: 5_000,
  circuitBreaker: { failures: 5, cooldownMs: 30_000 },
};

export async function runWithResilience<T>(fn: () => Promise<T>): Promise<T> {
  let lastError: unknown;
  for (let attempt = 1; attempt <= config.retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      await new Promise((r) => setTimeout(r, attempt * 250));
    }
  }
  throw lastError;
}
```

### 3. 真に重要な指標を計測する

| 指標 | 推奨される初期ターゲット |
| --- | --- |
| p95 レイテンシ | < 300 ms |
| エラーバジェット消費率 | < 2% / 30 日 |
| デプロイ頻度 | 毎日 (Daily) |
| ロールバック所要時間 | < 10 分 |

## 本番チェックリスト

1. モデルチェックポイント ID と評価スコアを付与した構造化ログを導入する。
2. 新旧モデルの出力を段階的に比較検証できる A/B テスト用の機能フラグを設定する。
3. リリース前に壊滅的忘却（Catastrophic Forgetting）の発生有無を総合評価ベンチマークで検証する。
4. 発生頻度の高い上位 3 つのモデル障害シナリオ（過学習によるループ出力、トークン長超過、ハルシネーション悪化）に対する運用手順書（Runbook）を整備する。

## よくある落とし穴

> 実際のユーザーが付く前にプラットフォームを過剰に作り込まないこと。早期に選んだ技巧的な技術よりも、適切に選ばれた堅実な技術のほうが遥かに成果を生みます。

- 頻繁に更新される外部の事実情報を、RAG ではなくファインチューニングで覚えさせようとすること。
- データの「質」を軽視してノイズ混じりの大量データを投入し、モデルの性能を破壊すること。
- 深夜の緊急呼び出しにつながる推論レイテンシスロットル警告の未設定。

## まとめ

**ドメイン特化LLMのファインチューン**は、小さく観測可能なステップで反復を重ねるチームに大きな成果をもたらします。上記のチェックリストを起点に、週に 1 つの課題を自動化し、エンジニアリングの成功を積み重ねていきましょう。
