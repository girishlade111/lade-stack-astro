## はじめに

多層キャッシュ、非同期メッセージキュー、データベースの読み取りレプリカ、そして水平シャーディング：100 万人以上のユーザー規模へ成長させるための段階的スケーリングプレイブックです。本ガイドでは、基本概念からトレードオフ、今週から現場へ導入できる本番仕様のワークフローまでを詳しく解説します。

## なぜ重要なのか

- **開発者ベロシティの向上**: 適切なデフォルト設計により、日々の突発的なスロークエリ対応や火消し作業を一掃します。
- **システムの信頼性向上**: キャンペーンや突発的なアクセス集中でもサービスを落とさない堅牢性を実現します。
- **コストコントロール**: 過剰なハイスペックサーバーへの場当たり的課金を防ぎ、スケールアウト効率を高めます。

## コアコンセプト

### 1. 最小の実装スライスから着手する

最初から複雑な分散シャーディングを導入するのではなく、まずはエンドツーエンドで動作する単一のバーティカルスライスを完成させます。**100万人を支えるSaaSスケーリング**においては、主要な読み取りトラフィックをリードレプリカへ逃がし、初日からのレイテンシ可観測性を確立することを意味します。

### 2. 「成功の落とし穴」を広く設ける

個々の開発者が独自にコネクション管理を行うのではなく、コネクションプーリング（PgBouncer 等）や自動キャッシュ再取得を共通化します。本番対応の最小スターター構成例：

```typescript
// Minimal production-ready starter
export const config = {
  retries: 3,
  timeoutMs: 5_000,
  circuitBreaker: { failures: 5, cooldownMs: 30_000 },
};

export async function runWithResilience<T>(fn: () => Promise<T>): Promise<T> {
  let lastError: unknown;
  for (let attempt = 1; attempt <= config.retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      await new Promise((r) => setTimeout(r, attempt * 250));
    }
  }
  throw lastError;
}
```

### 3. 真に重要な指標を計測する

| 指标 | 推奨される初期ターゲット |
| --- | --- |
| p95 レイテンシ | < 300 ms |
| エラーバジェット消費率 | < 2% / 30 日 |
| デプロイ頻度 | 毎日 (Daily) |
| ロールバック所要時間 | < 10 分 |

## 本番チェックリスト

1. グローバルなリクエスト ID とクエリ実行時間を紐付けた構造化ログを導入する。
2. 負荷急増時に重い機能を安全に停止できる縮退運転用の機能フラグ（Feature Flag）を設定する。
3. リリース前に読み取りレプリカのレプリケーション遅延（Replication Lag）耐性を検証する。
4. 発生頻度の高い上位 3 つの障害シナリオ（DB コネクション枯渇、キャッシュ雪崩、キュー滞留）に対する運用手順書（Runbook）を整備する。

## よくある落とし穴

> 実際のユーザーが付く前にプラットフォームを過剰に作り込まないこと。早期に選んだ技巧的な技術よりも、適切に選ばれた堅実な技術のほうが遥かに成果を生みます。

- 読み書きの分離やインデックス設計を行わないまま、安易にマイクロサービス分割へ逃げること。
- コネクションプールを設けず、サーバーレス関数からの直接接続で DB を落とすこと。
- 深夜の緊急呼び出しにつながるスロークエリ急増アラートの未設定。
