## はじめに

サイロ（分離型）、プール（共有型）、ブリッジ（ハイブリッド型）の 3 つのテナントモデルを比較し、データ分離、インフラコスト、スケーラビリティのトレードオフを検証します。本ガイドでは、基本概念からトレードオフ、今週から現場へ導入できる本番仕様のワークフローまでを詳しく解説します。

## なぜ重要なのか

- **開発者ベロシティの向上**: 適切なデフォルトの分離設計により、テナント境界のチェック漏れや煩雑な手動制御をなくします。
- **システムの信頼性向上**: 特定顧客のトラフィック集中による「ノイジーネイバー（近隣ノイズ）」から他のテナントを守ります。
- **コストコントロール**: リソース共有効率を高め、顧客あたりの限界コンピューティングコストを適正化します。

## コアコンセプト

### 1. 最小の実装スライスから着手する

最初から過剰に複雑なシャーディングを組む前に、まずはエンドツーエンドで動作する単一のバーティカルスライスを完成させます。**マルチテナントSaaSアーキテクチャ**においては、単一データベース内で Tenant ID によるコンテキスト注入と初日からの可観測性を確立することを意味します。

### 2. 「成功の落とし穴」を広く設ける

手動の SQL フィルタに頼るのではなく、Row-Level Security（RLS）やフレームワークのインターセプターを用いて、自然とデータ分離が保たれるようにします。本番対応の最小スターター構成例：

```typescript
// Minimal production-ready starter
export const config = {
  retries: 3,
  timeoutMs: 5_000,
  circuitBreaker: { failures: 5, cooldownMs: 30_000 },
};

export async function runWithResilience<T>(fn: () => Promise<T>): Promise<T> {
  let lastError: unknown;
  for (let attempt = 1; attempt <= config.retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      await new Promise((r) => setTimeout(r, attempt * 250));
    }
  }
  throw lastError;
}
```

### 3. 真に重要な指標を計測する

| 指標 | 推奨される初期ターゲット |
| --- | --- |
| p95 レイテンシ | < 300 ms |
| エラーバジェット消費率 | < 2% / 30 日 |
| デプロイ頻度 | 毎日 (Daily) |
| ロールバック所要時間 | < 10 分 |

## 本番チェックリスト

1. テナント ID とリクエスト ID を付与した構造化ログを導入する。
2. 特定テナント向けの段階的機能ロールアウトを可能にする機能フラグ（Feature Flag）を設定する。
3. リリース前に大規模テナントのデータ読み書き集中を想定したシミュレーションを実施する。
4. 発生頻度の高い上位 3 つの障害シナリオ（テナント分離リーク、クォータ枯渇、データベースマイグレーション遅延）に対する運用手順書（Runbook）を整備する。

## よくある落とし穴

> 実際のユーザーが付く前にプラットフォームを過剰に作り込まないこと。早期に選んだ技巧的な技術よりも、適切に選ばれた堅実な技術のほうが遥かに成果を生みます。

- アプリケーション側の WHERE 句だけに頼り、データベースレベルの RLS を設定しないこと。
- キャッシュキーにテナント ID プレフィックスを付け忘れ、別テナントへデータが混入すること。
- 深夜の緊急呼び出しにつながるテナント別クォータ枯渇アラートの未設定。

## まとめ

**マルチテナントSaaSアーキテクチャ**は、小さく観測可能なステップで反復を重ねるチームに大きな成果をもたらします。上記のチェックリストを起点に、週に 1 つの課題を自動化し、エンジニアリングの成功を積み重ねていきましょう。
