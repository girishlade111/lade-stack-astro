## はじめに

物理サーバーやコンテナの管理を完全に手放し、BaaS を駆使して高信頼な本番バックエンドを構築します：スキーマ設計、エッジ関数（Edge Functions）、そしてバックグラウンドジョブの設計まで。本ガイドでは、基本概念からトレードオフ、今週から現場へ導入できる本番仕様のワークフローまでを詳しく解説します。

## なぜ重要なのか

- **開発者ベロシティの向上**: OS のパッチ当てやインフラ管理作業から解放され、コアなビジネスロジックに集中できます。
- **システムの信頼性向上**: 世界各地のエッジ拠点で自動スケールするマネージド基盤の恩恵を享受できます。
- **コストコントロール**: 完全な「実行時間・実行回数に応じた従量課金」により、トラフィックが少ない立ち上げ期のコストを極小化します。

## コアコンセプト

### 1. 最小の実装スライスから着手する

複雑なイベント駆動ワークフローを組む前に、まずはエンドツーエンドで動作する単一のバーティカルスライスを完成させます。**BaaSでサーバーレスバックエンド**においては、エッジ関数経由で認証・データベース操作を行う単一の API エンドポイントを可観測性付きで構築することを意味します。

### 2. 「成功の落とし穴」を広く設ける

個々の関数内で場当たり的にエラーハンドリングを行うのではなく、共通のレスポンスフォーマッタやリトライラッパーを導入します。本番対応の最小スターター構成例：

```typescript
// Minimal production-ready starter
export const config = {
  retries: 3,
  timeoutMs: 5_000,
  circuitBreaker: { failures: 5, cooldownMs: 30_000 },
};

export async function runWithResilience<T>(fn: () => Promise<T>): Promise<T> {
  let lastError: unknown;
  for (let attempt = 1; attempt <= config.retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      await new Promise((r) => setTimeout(r, attempt * 250));
    }
  }
  throw lastError;
}
```

### 3. 真に重要な指標を計測する

| 指標 | 推奨される初期ターゲット |
| --- | --- |
| p95 レイテンシ | < 300 ms |
| エラーバジェット消費率 | < 2% / 30 日 |
| デプロイ頻度 | 毎日 (Daily) |
| ロールバック所要時間 | < 10 分 |

## 本番チェックリスト

1. エッジ関数名、実行時間、リクエスト ID を付与した構造化ログを導入する。
2. 重いバックグラウンド処理の実行可否を制御する機能フラグ（Feature Flag）を設定する。
3. リリース前にコールドスタート（Cold Start）時のレイテンシとメモリ上限を検証する。
4. 発生頻度の高い上位 3 つの障害シナリオ（タイムアウトエラー、コネクションプール枯渇、外部 API 障害）に対する運用手順書（Runbook）を整備する。

## よくある落とし穴

> 実際のユーザーが付く前にプラットフォームを過剰に作り込まないこと。早期に選んだ技巧的な技術よりも、適切に選ばれた堅実な技術のほうが遥かに成果を生みます。

- 長時間実行されるバッチ処理を、実行時間制限のあるサーバーレス関数で強引に動かすこと。
- データベース接続プールを介さず、関数の急増によってデータベースを枯渇させること。
- 深夜の緊急呼び出しにつながる関数実行エラー率スパイクのアラート未設定。

## まとめ

**BaaSでサーバーレスバックエンド**は、小さく観測可能なステップで反復を重ねるチームに大きな成果をもたらします。上記のチェックリストを起点に、週に 1 つの課題を自動化し、エンジニアリングの成功を積み重ねていきましょう。
