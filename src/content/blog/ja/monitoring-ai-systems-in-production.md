## はじめに

生成結果の品質、入力データや概念のドリフト、トークンコスト、そしてエンドツーエンドの応答遅延：評価メトリクス（Evals）とガードレールを本番推論ループに組み込み、実運用に耐えうる AI 監視システムを構築します。本ガイドでは、基本概念からトレードオフ、今週から現場へ導入できる本番仕様のワークフローまでを詳しく解説します。

## なぜ重要なのか

- **開発者ベロシティの向上**: 稼働中の品質スコアをリアルタイムで追跡することで、プロンプト改善やモデル更新の効果を客観的に評価できます。
- **システムの信頼性向上**: 不適切な出力やハルシネーション、プロンプトインジェクションをガードレールで即時検知・遮断します。
- **コストコントロール**: ユーザー別・機能別のトークン消費を追跡し、無限ループや異常なバッチ呼び出しによる過剰請求を未然に防ぎます。

## コアコンセプト

### 1. 最小の実装スライスから着手する

全機能に一挙に高度なマルチモデル評価を導入する前に、まずはエンドツーエンドで動作する単一のバーティカルスライスを完成させます。**本番AIシステムの監視**においては、主要な 1 つの AI 機能に対してプロンプト、完了結果、レイテンシ、トークン数を初日から記録することを意味します。

### 2. 「成功の落とし穴」を広く設ける

個々の呼び出し箇所でログ出力を手書きするのではなく、API ラッパー経由でメタデータと品質評価が自動付与されるようにします。本番対応の最小スターター構成例：

```typescript
// Minimal production-ready starter
export const config = {
  retries: 3,
  timeoutMs: 5_000,
  circuitBreaker: { failures: 5, cooldownMs: 30_000 },
};

export async function runWithResilience<T>(fn: () => Promise<T>): Promise<T> {
  let lastError: unknown;
  for (let attempt = 1; attempt <= config.retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      await new Promise((r) => setTimeout(r, attempt * 250));
    }
  }
  throw lastError;
}
```

### 3. 真に重要な指標を計測する

| 指標 | 推奨される初期ターゲット |
| --- | --- |
| p95 レイテンシ | < 300 ms |
| エラーバジェット消費率 | < 2% / 30 日 |
| デプロイ頻度 | 毎日 (Daily) |
| ロールバック所要時間 | < 10 分 |

## 本番チェックリスト

1. セッション ID、プロンプトハッシュ、トークン使用量を紐付けた構造化ログを導入する。
2. ガードレール違反が多発した際に安全な定型文レスポンスへフォールバックする機能フラグを設定する。
3. リリース前に過去のプロンプトログを用いた回帰評価テスト（Evals Benchmark）を実施する。
4. 発生頻度の高い上位 3 つの障害シナリオ（プロバイダー障害時のタイムアウト、出力品質の急激なドリフト、トークン消費スパイク）に対する運用手順書（Runbook）を整備する。

## よくある落とし穴

> 実際のユーザーが付く前にプラットフォームを過剰に作り込まないこと。早期に選んだ技巧的な技術よりも、適切に選ばれた堅実な技術のほうが遥かに成果を生みます。

- HTTP ステータス 200 だけを監視し、モデルが返した「申し訳ありませんが回答できません」等の意味論的エラーを見逃すこと。
- 個人識別情報（PII）をマスクせずに、平文のままログ収集サービスへ送信すること。
- 深夜の緊急呼び出しにつながるプロバイダーレート制限超過アラートの未設定。

## まとめ

**本番AIシステムの監視**は、小さく観測可能なステップで反復を重ねるチームに大きな成果をもたらします。上記のチェックリストを起点に、週に 1 つの課題を自動化し、エンジニアリングの成功を積み重ねていきましょう。
