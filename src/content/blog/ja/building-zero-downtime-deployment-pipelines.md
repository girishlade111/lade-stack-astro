## はじめに

ブルーグリーンデプロイ、カナリアリリース、ローリングアップデートとヘルスゲート（レディネスプローブ）：エンドユーザーに一切の接続断やエラーを意識させない無停止デプロイを実現します。本ガイドでは、基本概念からトレードオフ、今週から現場へ導入できる本番仕様のワークフローまでを詳しく解説します。

## なぜ重要なのか

- **開発者ベロシティの向上**: メンテナンステストのための深夜作業や休日出勤をなくし、日中の頻繁なリリースを可能にします。
- **システムの信頼性向上**: 異常検知時にトラフィックを即時切り戻せる安全弁を組み込みます。
- **コストコントロール**: ダウンタイムに伴う売上機会の損失や SLA 違反ペナルティを未然に防止します。

## コアコンセプト

### 1. 最小の実装スライスから着手する

複雑なメッシュルーティングを構築する前に、まずはエンドツーエンドで動作する単一のバーティカルスライスを完成させます。**無停止デプロイパイプライン**においては、単一サービスのローリング更新とヘルスチェックによる自動切り替えから着手し、初日から可観測性を確保します。

### 2. 「成功の落とし穴」を広く設ける

手動の切り替え手順書に頼るのではなく、デプロイパイプライン自体にヘルス検証と自動ロールバックを組み込みます。本番対応の最小スターター構成例：

```typescript
// Minimal production-ready starter
export const config = {
  retries: 3,
  timeoutMs: 5_000,
  circuitBreaker: { failures: 5, cooldownMs: 30_000 },
};

export async function runWithResilience<T>(fn: () => Promise<T>): Promise<T> {
  let lastError: unknown;
  for (let attempt = 1; attempt <= config.retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      await new Promise((r) => setTimeout(r, attempt * 250));
    }
  }
  throw lastError;
}
```

### 3. 真に重要な指標を計測する

| 指標 | 推奨される初期ターゲット |
| --- | --- |
| p95 レイテンシ | < 300 ms |
| エラーバジェット消費率 | < 2% / 30 日 |
| デプロイ頻度 | 毎日 (Daily) |
| ロールバック所要時間 | < 10 分 |

## 本番チェックリスト

1. デプロイバージョンとリクエスト ID を紐付けた構造化ログを導入する。
2. 問題発生時に新バージョンへのトラフィックを遮断するキルスイッチを整備する。
3. リリース前に新旧バージョンの並行稼働によるデータベーススキーマの後方互換性を検証する。
4. 発生頻度の高い上位 3 つの障害シナリオ（ヘルスチェック失敗、コネクションリーク、スキーマ不整合）に対する運用手順書（Runbook）を整備する。

## よくある落とし穴

> 実際のユーザーが付く前にプラットフォームを過剰に作り込まないこと。早期に選んだ技巧的な技術よりも、適切に選ばれた堅実な技術のほうが遥かに成果を生みます。

- データベースの破壊的マイグレーションをアプリのデプロイと同時に実行してしまうこと。
- グレースフルシャットダウン（SIGTERM 処理）が実装されておらず、処理中のリクエストが切断されること。
- 深夜の緊急呼び出しにつながるエラー率スパイクのアラート未設定。

## まとめ

**無停止デプロイパイプライン**は、小さく観測可能なステップで反復を重ねるチームに大きな成果をもたらします。上記のチェックリストを起点に、週に 1 つの課題を自動化し、エンジニアリングの成功を積み重ねていきましょう。
