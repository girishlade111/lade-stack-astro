## はじめに

正当な一般クライアントに不便を強いることなく、トークンバケット、スライディングウィンドウ、テナント別クォータ設計によって API を確実に保護します。本ガイドでは、基本概念からトレードオフ、今週から現場へ導入できる本番仕様のワークフローまでを詳しく解説します。

## なぜ重要なのか

- **開発者ベロシティの向上**: 適切なデフォルト設計により、不規則なトラフィックに対する場当たり的な防御コードの作成を一掃します。
- **システムの信頼性向上**: 悪意あるアクセスやバグによる過剰リクエストからバックエンドリソースを守り抜きます。
- **コストコントロール**: サーバーレス実行回数や外部 API 呼び出しの上限超過による予期せぬクラウド請求を未然に遮断します。

## コアコンセプト

### 1. 最小の実装スライスから着手する

分散キャッシュを用いた全社的クォータ基盤を設計する前に、まずはエンドツーエンドで動作する単一のバーティカルスライスを完成させます。**APIレート制限とスロットリング**においては、API ゲートウェイやミドルウェア層における単一エンドポイントのレート制限ルールと、初日からの可観測性確立を意味します。

### 2. 「成功の落とし穴」を広く設ける

複雑なドキュメントでクライアントに対処を求めるのではなく、標準的な HTTP ヘッダー（`Retry-After`, `RateLimit-Remaining`）を正確に返却し、自己修復的なリトライを促します。本番対応の最小スターター構成例：

```typescript
// Minimal production-ready starter
export const config = {
  retries: 3,
  timeoutMs: 5_000,
  circuitBreaker: { failures: 5, cooldownMs: 30_000 },
};

export async function runWithResilience<T>(fn: () => Promise<T>): Promise<T> {
  let lastError: unknown;
  for (let attempt = 1; attempt <= config.retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      await new Promise((r) => setTimeout(r, attempt * 250));
    }
  }
  throw lastError;
}
```

### 3. 真に重要な指標を計測する

| 指標 | 推奨される初期ターゲット |
| --- | --- |
| p95 レイテンシ | < 300 ms |
| エラーバジェット消費率 | < 2% / 30 日 |
| デプロイ頻度 | 毎日 (Daily) |
| ロールバック所要時間 | < 10 分 |

## 本番チェックリスト

1. クライアント IP / テナント ID とリクエスト ID を紐付けた構造化ログを導入する。
2. 緊急時に制限値を即座に変更またはバイパスできる機能フラグ（Feature Flag）を設ける。
3. リリース前にバーストトラフィックに対する挙動とキャッシュ負荷を検証する。
4. 発生頻度の高い上位 3 つの障害シナリオ（Redis 接続障害時のフェイルオープン、誤検知による正規ユーザーのブロック、DDoS 攻撃）に対する運用手順書（Runbook）を整備する。

## よくある落とし穴

> 実際のユーザーが付く前にプラットフォームを過剰に作り込まないこと。早期に選んだ技巧的な技術よりも、適切に選ばれた堅実な技術のほうが遥かに成果を生みます。

- 共有メモリに頼る単純なインメモリ制限を採用し、複数台構成でレート制限が機能しないこと。
- レート制限超過時に 429 ではなく 500 エラーを返し、クライアントが誤認して再試行を加速させること。
- 深夜の緊急呼び出しにつながる拒否率スパイクのアラート未設定。

## まとめ

**APIレート制限とスロットリング**は、小さく観測可能なステップで反復を重ねるチームに大きな成果をもたらします。上記のチェックリストを起点に、週に 1 つの課題を自動化し、エンジニアリングの成功を積み重ねていきましょう。
