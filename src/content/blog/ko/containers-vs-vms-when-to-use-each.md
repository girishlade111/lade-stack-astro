## 소개

보안 격리 수준, 리소스 오버헤드, 그리고 일상적인 운영 관리의 차이: 컨테이너와 가상 머신(VM) 사이의 실질적인 기술적 트레이드오프를 비교하여, 언제 무엇을 단독으로 혹은 혼합하여 사용해야 하는지 명쾌한 기준을 제시합니다. 본 글에서는 핵심 개념, 아키텍처적 트레이드오프, 그리고 이번 주에 바로 팀에 적용할 수 있는 프로덕션 수준의 워크플로를 다룹니다.

## 왜 중요한가

- **개발자 생산성 향상**: 로컬 개발 환경, CI 파이프라인, 프로덕션 클러스터의 환경 일치성을 확보하여 '내 컴퓨터에서는 잘 동작하는데' 문제를 영구히 해결합니다.
- **시스템 신뢰성 확보**: 신뢰할 수 없는 다중 테넌트 코드 실행 환경에서 하이퍼바이저 수준의 단단한 격리 계층으로 호스트 시스템을 안전하게 보호합니다.
- **비용 통제**: 컨테이너의 고밀도 패킹을 통해 유휴 서버 대수를 줄이고 인프라 하드웨어 비용을 최적화합니다.

## 핵심 개념

### 1. 가장 작은 동작 단위에서 시작하기

전체 시스템을 한 번에 컨테이너나 VM으로 전면 이전하려 하지 말고, 엔드투엔드로 동작하는 수직 슬라이스 하나를 먼저 완성하십시오. **컨테이너 vs VM: 언제 뭘 쓸까**의 관점에서는 단일 상태 비저장(Stateless) 서비스를 대상으로 컨테이너 빌드 및 배포를 검증하고 첫날부터 가시성을 확보하는 것을 의미합니다.

### 2. 성공의 함정을 넓게 파두기

개발자 개개인이 임의의 베이스 이미지를 사용하지 않도록, 보안 패치된 경량 표준 이미지(Distroless/Alpine)를 사내 기본 템플릿으로 제공하십시오. 프로덕션 환경을 위한 스타터 예시:

```typescript
// Minimal production-ready starter
export const config = {
  retries: 3,
  timeoutMs: 5_000,
  circuitBreaker: { failures: 5, cooldownMs: 30_000 },
};

export async function runWithResilience<T>(fn: () => Promise<T>): Promise<T> {
  let lastError: unknown;
  for (let attempt = 1; attempt <= config.retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      await new Promise((r) => setTimeout(r, attempt * 250));
    }
  }
  throw lastError;
}
```

### 3. 본질적인 지표 측정하기

| 지표 | 권장 시작 목표치 |
| --- | --- |
| p95 응답 지연 시간 | < 300 ms |
| 에러 버짓 소진율 | < 2% / 30 일 |
| 배포 빈도 | 매일 (Daily) |
| 롤백 소요 시간 | < 10 분 |

## 프로덕션 체크리스트

1. 호스트 노드명과 컨테이너 인스턴스 ID가 포함된 구조화된 로그를 수집합니다.
2. 장애 발생 시 컨테이너를 안전하게 드레인(Drain)하고 재시작할 수 있는 기능 플래그를 마련합니다.
3. 정식 런칭 전에 cgroup 메모리 제한 도달(OOM) 시 컨테이너의 그레이스풀 셧다운 동작을 검증합니다.
4. 발생 빈도가 높은 상위 3가지 장애 시나리오(이미지 풀 실패, 노드 디스크 고갈, PID 리소스 한도 도달)에 대한 런북(Runbook)을 작성합니다.

## 흔한 실수와 주의점

> 실제 사용자를 확보하기 전에 플랫폼을 과도하게 설계하지 마십시오. 초기에 선택한 화려한 기술보다 적재적소에 잘 고른 지루하고 검증된 기술이 언제나 승리합니다.

- 비대해진 레거시 모놀리스를 단일 컨테이너에 억지로 집어넣고 VM처럼 수동 운영하는 행위.
- 신뢰할 수 없는 임의 코드를 단순 리눅스 네임스페이스 격리만으로 실행하여 커널 탈출 위험을 방치하는 문제.
- 새벽 3시에 온콜 엔지니어를 깨워야 하는 컨테이너 OOM Kill 급증 알림 누락.

## 결론

**컨테이너 vs VM: 언제 뭘 쓸까**는 작고 명확하게 관측 가능한 단위로 기민하게 반복하는 엔지니어링 팀에 큰 보상을 안겨줍니다. 위의 체크리스트를 시작점으로 삼아 매주 하나의 병목을 자동화하고 시스템의 완성도를 높여가십시오.
