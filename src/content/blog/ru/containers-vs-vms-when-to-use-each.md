## Введение

Уровень аппаратной изоляции, накладные расходы на ядро операционной системы и повседневные задачи эксплуатации: детальное сравнение контейнеров и виртуальных машин (ВМ) для уверенного выбора подходящего инструмента. В этом руководстве рассматриваются ключевые концепции, выбор подходов и готовый продакшен-пайплайн.

## Почему это важно

- **Скорость инженерной команды**: гарантированная идентичность окружения разработки, тестирования и продакшена устраняет проблему «на моем ноутбуке все работало».
- **Надежность системы**: использование жесткой изоляции на уровне гипервизора при запуске недоверенного кода или разделении чувствительных тенантов.
- **Контроль затрат**: высокая плотность размещения контейнеров на одном физическом узле сокращает расходы на инфраструктуру.

## Ключевые концепции

### 1. Начните с минимально жизнеспособного сквозного среза

Прежде чем переводить всю систему на контейнеры или ВМ, постройте сквозной вертикальный срез. Для темы **контейнеров или виртуальных машин: что выбрать** это означает контейнеризацию одного сервиса без сохранения состояния (stateless) с автоматическим контролем состояния с первого дня.

### 2. Сделайте правильный путь самым простым

Вместо самостоятельного написания тяжелых Dockerfile используйте стандартизированные безопасные базовые образы (Distroless или Alpine). Пример минимального продакшен-стартера:

```typescript
// Minimal production-ready starter
export const config = {
  retries: 3,
  timeoutMs: 5_000,
  circuitBreaker: { failures: 5, cooldownMs: 30_000 },
};

export async function runWithResilience<T>(fn: () => Promise<T>): Promise<T> {
  let lastError: unknown;
  for (let attempt = 1; attempt <= config.retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      await new Promise((r) => setTimeout(r, attempt * 250));
    }
  }
  throw lastError;
}
```

### 3. Измеряйте то, что действительно имеет значение

| Метрика | Рекомендуемый ориентир |
| --- | --- |
| Задержка p95 | < 300 ms |
| Расход бюджета ошибок | < 2% / 30 дней |
| Частота релизов | Ежедневно (Daily) |
| Время отката | < 10 минут |

## Чек-лист готовности к продакшену

1. Внедрите сбор логов с идентификацией имени хост-ноды и ID контейнера.
2. Предусмотрите возможность безопасного вывода нод из пула (drain) при проведении регламентных работ.
3. Протестируйте реакцию контейнера на сигнал SIGTERM и поведение приложения при нехватке памяти (OOMKilled).
4. Разработайте четкие инструкции (Runbooks) для трех сценариев: сбой скачивания образа, исчерпание дескрипторов процессов (PIDs), переполнение диска ноды.

## Типичные ошибки

> Не занимайтесь преждевременной оптимизацией и украшательством платформы до появления реальных пользователей. Простые, проверенные временем технологии всегда превосходят избыточно сложные решения, внедренные слишком рано.

- Помещение гигантского монолита в один контейнер и эксплуатация его как виртуальной машины с ручным входом по SSH.
- Запуск недоверенного клиентского кода внутри стандартных контейнеров без изоляции на уровне гипервизора (Kata/gVisor).
- Отсутствие мониторинга лимитов памяти cgroup.

## Заключение

**Контейнеры или виртуальные машины: что выбрать** дает максимальную отдачу тем командам, которые двигаются небольшими, прозрачными и контролируемыми шагами. Воспользуйтесь чек-листом выше, автоматизируйте по одной проблемной точке в неделю и последовательно закрепляйте инженерные победы.
