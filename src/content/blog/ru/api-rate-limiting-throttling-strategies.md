## Введение

Защита API с помощью алгоритмов Token Bucket, скользящего окна (Sliding Window) и индивидуальных квот по тенантам без создания помех добросовестным клиентам. В этом материале рассматриваются фундаментальные концепции, выбор подходов и готовый продакшен-пайплайн ограничения нагрузки.

## Почему это важно

- **Скорость инженерной команды**: единые правила защиты на уровне шлюза избавляют разработчиков сервисов от написания самодельных фильтров в каждом контроллере.
- **Надежность системы**: гарантированная защита баз данных и вычислительных узлов от DDoS-атак, сканеров уязвимостей и зациклившихся клиентов.
- **Контроль затрат**: предотвращение неконтролируемого перерасхода бюджета из-за взрывного роста вызовов serverless-функций или внешних платных API.

## Ключевые концепции

### 1. Начните с минимально жизнеспособного сквозного среза

Прежде чем внедрять сложную распределенную иерархию квот, постройте сквозной вертикальный срез. Для темы **стратегий ограничения частоты запросов и троттлинга API** это означает настройку лимитов для одного критического публичного эндпоинта с передачей метрик в систему мониторинга.

### 2. Сделайте правильный путь самым простым

Возвращайте клиентам стандартные HTTP-заголовки (`Retry-After`, `RateLimit-Remaining`), чтобы внешние SDK могли автоматически применять экспоненциальную задержку. Пример минимального продакшен-стартера:

```typescript
// Minimal production-ready starter
export const config = {
  retries: 3,
  timeoutMs: 5_000,
  circuitBreaker: { failures: 5, cooldownMs: 30_000 },
};

export async function runWithResilience<T>(fn: () => Promise<T>): Promise<T> {
  let lastError: unknown;
  for (let attempt = 1; attempt <= config.retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      await new Promise((r) => setTimeout(r, attempt * 250));
    }
  }
  throw lastError;
}
```

### 3. Измеряйте то, что действительно имеет значение

| Метрика | Рекомендуемый ориентир |
| --- | --- |
| Задержка p95 | < 300 ms |
| Расход бюджета ошибок | < 2% / 30 дней |
| Частота релизов | Ежедневно (Daily) |
| Время отката | < 10 минут |

## Чек-лист готовности к продакшену

1. Логируйте идентификатор клиента (IP, User ID, Tenant ID) вместе с Request ID и статусом лимита.
2. Реализуйте фиче-флаг для оперативного смягчения или отключения ограничений при ложных срабатываниях.
3. Протестируйте устойчивость Redis-хранилища счетчиков к высоким пиковым нагрузкам.
4. Разработайте четкие инструкции (Runbooks) для трех ключевых сценариев: недоступность Redis (политика Fail-Open), атака ботов, блокировка ключевых партнеров.

## Типичные ошибки

> Не занимайтесь преждевременной оптимизацией и украшательством платформы до появления реальных пользователей. Простые, проверенные временем технологии всегда превосходят избыточно сложные решения, внедренные слишком рано.

- Использование локальных in-memory счетчиков на экземплярах за балансировщиком, из-за чего реальный лимит умножается на число подов.
- Возврат кода ошибки 500 вместо 429 Too Many Requests при превышении квоты.
- Отсутствие мониторинга доли отклоненных запросов (429 rate).

## Заключение

**Стратегии ограничения частоты запросов и троттлинга API** дают максимальную отдачу тем командам, которые двигаются небольшими, прозрачными и контролируемыми шагами. Воспользуйтесь чек-листом выше, автоматизируйте по одной проблемной точке в неделю и последовательно закрепляйте инженерные победы.
