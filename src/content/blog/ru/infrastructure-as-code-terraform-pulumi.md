## Введение

Декларативный предметно-ориентированный язык HCL или полноценные языки общего назначения (TypeScript, Python, Go)? Управление файлом состояния (State), механизмы блокировок и архитектура переиспользуемых модулей: детальное сравнение Terraform и Pulumi для построения надежной платформы Infrastructure as Code. В этом руководстве рассматриваются ключевые концепции, выбор подходов и готовый продакшен-пайплайн.

## Почему это важно

- **Скорость инженерной команды**: декларативное описание ресурсов позволяет развернуть идентичную копию тестового окружения за считанные минуты.
- **Надежность системы**: обязательное предварительное планирование изменений (Plan/Preview) предотвращает случайное удаление продакшен-ресурсов.
- **Контроль затрат**: интеграция инструментов статического анализа расходов (например, Infracost) прямо в процесс Pull Request для упреждающего контроля бюджета.

## Ключевые концепции

### 1. Начните с минимально жизнеспособного сквозного среза

Прежде чем пытаться импортировать всю историческую облачную инфраструктуру в код, постройте сквозной вертикальный срез. Для темы **инфраструктуры как код: Terraform против Pulumi** это означает перевод одной подсети VPC или S3-бакета под управление IaC с автоматической проверкой Plan в CI.

### 2. Сделайте правильный путь самым простым

Вместо написания ресурсов с нуля предоставьте разработчикам проверенные внутренние библиотеки модулей со встроенными требованиями безопасности. Пример минимального продакшен-стартера:

```typescript
// Minimal production-ready starter
export const config = {
  retries: 3,
  timeoutMs: 5_000,
  circuitBreaker: { failures: 5, cooldownMs: 30_000 },
};

export async function runWithResilience<T>(fn: () => Promise<T>): Promise<T> {
  let lastError: unknown;
  for (let attempt = 1; attempt <= config.retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      await new Promise((r) => setTimeout(r, attempt * 250));
    }
  }
  throw lastError;
}
```

### 3. Измеряйте то, что действительно имеет значение

| Метрика | Рекомендуемый ориентир |
| --- | --- |
| Задержка p95 | < 300 ms |
| Расход бюджета ошибок | < 2% / 30 дней |
| Частота релизов | Ежедневно (Daily) |
| Время отката | < 10 минут |

## Чек-лист готовности к продакшену

1. Внедрите аудит-логи изменений состояния с фиксацией автора и контрольной суммы стейта.
2. Настройте защитные барьеры, блокирующие непреднамеренное удаление (Destroy) критических ресурсов.
3. Добавьте в CI статические сканеры безопасности манифестов (tfsec, Checkov).
4. Разработайте четкие инструкции (Runbooks) для трех сценариев: зависшая блокировка стейта, коллизия имен ресурсов, циклическая зависимость модулей.

## Типичные ошибки

> Не занимайтесь преждевременной оптимизацией и украшательством платформы до появления реальных пользователей. Простые, проверенные временем технологии всегда превосходят избыточно сложные решения, внедренные слишком рано.

- Хранение всей инфраструктуры компании в одном монолитном файле состояния, из-за чего выполнение plan занимает десятки минут.
- Отсутствие распределенной блокировки стейта (например, через DynamoDB), приводящее к повреждению файла при одновременном запуске.
- Отсутствие мониторинга рассинхронизации реальной инфраструктуры со стейтом (дрейф параметров).

## Заключение

**Инфраструктура как код: Terraform против Pulumi** дает максимальную отдачу тем командам, которые двигаются небольшими, прозрачными и контролируемыми шагами. Воспользуйтесь чек-листом выше, автоматизируйте по одной проблемной точке в неделю и последовательно закрепляйте инженерные победы.
